# 設計判断の記録

設計書（[`design.md`](design.md)）に載っている「何をするか」に対して、ここには「なぜそう決めたか」と「何を選ばなかったか」を残す。新しい判断は末尾に足し、番号は振り直さない。判断を覆すときは古い項目を消さず、覆した項目から参照する。

## 書き方

```markdown
## D-NNN: 判断の要約（一文）

- 日付: YYYY-MM-DD
- 状態: 採用 / 撤回（D-MMM で置き換え）

**背景:** なぜ決める必要があったか。

**判断:** 何に決めたか。

**選ばなかった案:** 何を検討し、なぜ選ばなかったか。
```

## D-001: AI 処理は Paperless とは別のコンテナにし、REST API 越しに動かす

- 日付: 2026-10-27
- 状態: 採用

**背景:** Paperless-ngx には取り込み時のスクリプト（pre/post consume script）や、LLM を使う既製の拡張（paperless-gpt など）がある。

**判断:** 自作のコンテナから REST API だけを使って書き戻す。Paperless 本体のイメージには手を入れない。

**選ばなかった案:** consume script は Paperless のコンテナ内で動くため、Claude Code CLI と Node.js をそのイメージに入れる必要があり、Paperless の更新のたびに作り直しになる。paperless-gpt は API キーを前提にしており、サブスクリプションプランの `claude -p` では動かせない（Claude が使えなくなったときの代替案としては残す）。

## D-002: LLM は API キーではなく `claude -p` とサブスクリプションプランで動かす

- 日付: 2026-10-27
- 状態: 採用

**背景:** 書類の量は家庭の範囲で、1 件あたりの処理は本文 8,000 文字程度。

**判断:** `CLAUDE_CODE_OAUTH_TOKEN` で `claude -p` を呼ぶ。利用枠の上限に達した書類は失敗として数えず、`ai-todo` のまま次の周期を待つ。

**選ばなかった案:** API の従量課金は、別に契約しているサブスクリプションの枠で足りる処理に追加の費用がかかる。非対話利用の扱いが変わった場合の代替案として残す（設計書 12 章）。

## D-003: 本文の空白以外の文字が 100 文字未満なら PDF を読ませる

- 日付: 2026-10-27
- 状態: 採用

**背景:** 設計書は「OCR が崩れている書類」には PDF を直接読ませるとしているが、崩れているかどうかの判定基準を決めていなかった。

**判断:** 本文から空白を除いた文字数が 100 文字未満なら、本文ではなく PDF を Read ツールで読ませる。

**選ばなかった案:** OCR の信頼度で判定する案は、Paperless の API から信頼度を取れない。判定を人に任せる案は、書類ごとの手作業が増える。

## D-004: `claude` のタイムアウトと、書類単位の PATCH・ダウンロードの 400/404 は書類起因の失敗として数える

- 日付: 2026-10-27
- 状態: 採用

**背景:** 書類起因の失敗を JSON の破損と検証エラーだけに限ると、`claude` がタイムアウトする書類や、PATCH が 400 を返す書類は、利用枠の上限などと同様に「その周期を打ち切る」扱いになる。すると 1 件が毎周期、ほかの書類の処理を止め続ける。

**判断:** `claude` のタイムアウトと、その書類に対する PATCH・ダウンロードの 400/404 は書類起因の失敗として数え、3 回で `ai-failed` にする。

**選ばなかった案:** 周期を打ち切る案は、上記のとおり 1 件の書類が全体を止める。

## D-005: 必須タグは ai-classifier が作らず、無ければ起動時に止める

- 日付: 2026-10-27
- 状態: 採用

**背景:** 状態管理用のタグが無いと分類結果を付け替えられない。ai-classifier が作る案もある。

**判断:** タグは人が作る。無ければ起動時にタグ名を示して止まる。

**選ばなかった案:** 自動で作る案は、ai-classifier のユーザーにタグの追加権限が要る。権限を最小にする方針（設計書 9 章）に反する。

## D-006: 同じ周期で新しく作った発行元・文書タイプは、後の書類では既存として使う

- 日付: 2026-10-27
- 状態: 採用

**背景:** 同じ周期に同じ新規の発行元が出てくる書類が複数あると、2 件目以降も「新規作成」になり、すべて `ai-review` に回るか、同名の発行元が重複して作られるおそれがある。

**判断:** 同じ周期で新しく作った発行元・文書タイプは、後の書類では既存として使う。2 件目は `ai-review` に回さない。最初の書類が `ai-review` に入り、人が Paperless で名前を直すか統合すれば、同じ発行元を使う両方の書類に反映されるため。このため、AI が作った名前は削除せず、名前の変更か統合で直す（削除すると、確認待ちに入らなかった 2 件目以降の書類から発行元・文書タイプが黙って外れる）。

**選ばなかった案:** 2 件目以降もすべて `ai-review` に回す案は、確認の手間が増えるだけで、直す箇所は 1 つのままである。

## D-007: `ai-failed` への付け替え自体が 400/404 で失敗したときは、失敗回数を消さない

- 日付: 2026-10-27
- 状態: 採用

**背景:** 失敗が 3 回に達した書類を `ai-failed` に付け替える PATCH 自体が 400/404 で失敗することがある。このとき失敗回数を消すと、書類は `ai-todo` のまま 0 回から数え直しになる。

**判断:** 失敗回数を消さず、次の周期でもう一度 `ai-failed` への付け替えを試みる。周期の中で書類を処理する前に失敗回数を確かめ、既に上限（3 回）に達していれば `claude` を呼ばずに `ai-failed` への付け替えだけをやり直す。付け替えがまた 400/404 で失敗しても回数は残す。

**選ばなかった案:** 失敗回数を消して数え直す案は、付け替えられない書類が毎周期 `claude` を呼び続ける。回数を残したまま毎周期判定し直す案も、上限に達した書類のために `claude` を呼び続け、たまたま判定が通れば `ai-failed` を経ずに結果が書き戻されてしまう。

## D-008: `claude` の「入力が長すぎる」エラーと大きすぎる PDF は書類起因の失敗として数える

- 日付: 2026-10-27
- 状態: 採用

**背景:** `claude -p` が `is_error` を返すと、これまでは一律に利用枠・認証の問題とみなして周期を打ち切っていた。しかし入力が長すぎるエラーは書類そのものが原因で、同じ書類を何度送っても同じエラーになる。この書類が `ai-todo` の先頭にある限り、後ろの書類が永久に処理されない。巨大な PDF も同じことを起こす。

**判断:** `is_error` のとき、`result`（CLI のエラーメッセージ）の先頭 200 文字をログに出す。`result` に `prompt is too long`（大文字小文字は区別しない）が含まれれば書類起因の失敗として数える。PDF を読ませる前に、原本が 20 MiB を超えていれば `claude` を呼ばずに書類起因の失敗にする。

CLI が返すエラーの正確な文面は確かめていない。文面が違えば、そのエラーは従来どおり周期を打ち切る側に倒れる。未知のエラーは周期を打ち切る扱いのままにし、書類の失敗として数え過ぎないようにする。

**選ばなかった案:** `error_max_turns` 以外の `is_error` をすべて書類起因にする案は、利用枠の上限や認証切れで全書類が 3 回で `ai-failed` に送られてしまう。

## D-009: 発行元・文書タイプを新規作成した書類は、書き戻しが済むまで記録し、再試行でも `ai-review` に回す

- 日付: 2026-10-27
- 状態: 採用

**背景:** 新規作成した発行元・文書タイプは `ai-review` に回す決まりである（設計書 7 章）。しかし作成の後で書類の PATCH が 400 などで失敗すると、書類は `ai-todo` のまま再試行になる。次の試行では作った名前が既存として見えるため、AI が作った名前が人の確認を経ずに `ai-done` へ進んでしまう。

**判断:** 発行元・文書タイプの作成の API を呼ぶ**前に**、その書類 ID を `STATE_DIR/created.json` に記録する。記録のある書類は判定結果にかかわらず「前回の試行で発行元・文書タイプを新規作成」を理由に `ai-review` に回す。記録は書類の PATCH が成功したとき、または `ai-failed` に移したときに消す。

作成の後に記録すると、Paperless が作成を確定した後で接続が切れる・プロセスが終わると、名前だけが残って記録が残らない。次の試行では名前が既存として一致し、`confident: true` なら `ai-done` へ抜ける。作成の前に記録すればこの穴はない。代わりに、Paperless が作成を拒んだ（400 など）場合にも記録が残り、その書類の再試行は必ず `ai-review` になる。人の確認が 1 回増えるだけなので受け入れる。

`created.json` が無いときは空とみなす（初回起動）。あるのに読めない・JSON でない・整数の配列でないときは、空とみなして進むと記録済みの書類まで確認を経ずに通るので、書類に起因しない失敗（`ServiceUnavailable`）としてその周期を打ち切り、ファイルの場所を ERROR で 1 行ログに出す（中身は出さない）。ファイルは上書きしないので、人が直すか消すまで分類は止まる。失敗回数の `failures.json` は、壊れても回数がやり直しになるだけなので、これまでどおり空とみなして進む。

**選ばなかった案:** Paperless 側の作成日時や作成者から AI が作った名前かを判定する案は、専用ユーザーに追加の参照権限が要り、手で作った名前との区別もあいまいになる。作成を PATCH の後に回す案は、PATCH に発行元の ID が要るので成り立たない。作成する名前まで journal に残して再試行時に照合する案は、名前の無害化・照合の規則を二重に持つことになるうえ、上の「拒まれても review」との差は確認 1 回分しかない。

## D-010: `claude` が応答の JSON を返さない失敗は、障害を示す語が無ければ書類起因として数え、連続したら周期を打ち切る

- 日付: 2026-10-27
- 状態: 採用

**背景:** `claude -p` の stdout が空・JSON でない・オブジェクトでないときは、一律に書類に起因しない失敗として周期を打ち切っていた。壊れた PDF で CLI が落ちるなど、1 件の入力でだけ再現する失敗でもそうなるので、その書類が `ai-todo` の先頭に残る限り、毎周期同じ位置で止まって後ろの書類が処理されない（D-008 と同じ問題）。

**判断:** 応答の JSON が無いときは、終了コードと stderr の先頭 200 文字をログに出したうえで、stderr を小文字にして認証・利用枠・ネットワークを示す語（`auth` `login` `token` `401` `403` `rate limit` `usage limit` `quota` `network` `econnrefused` `econnreset` `enotfound` `etimedout` `getaddrinfo` `socket`）を探す。含めば従来どおり書類に起因しない失敗（`ServiceUnavailable`）として周期を打ち切る。含まなければ書類に起因する失敗の一種 `CliFailure` として数える。

これだけだと、上の語を含まない文面で障害が起きたとき、`ai-todo` の書類が次々に数えられ、3 周期で全部 `ai-failed` に送られてしまう。そこで同じ周期の中で、直前に処理した書類も `CliFailure` で終わっていたら、2 件目は数えずに周期を打ち切る。こうすると、知らない文面の障害で数えられる書類は 1 周期に 1 件までになる。間に成功や別の種類の失敗を挟めば連続とはみなさない。周期をまたいでは持ち越さない。失敗回数の上限に達していて判定し直さずに `ai-failed` へ送る書類（D-007）は、`claude` を呼ばないので連続の判定に影響しない。

**選ばなかった案:** 従来どおり一律に周期を打ち切る案は、1 件の壊れた入力で列全体が止まる。一律に書類起因として数える案は、知らない文面の障害で全書類を `ai-failed` に送り得る。終了コードで分ける案は、CLI の終了コードの意味が文書化されておらず、障害と入力の不具合を区別できない。

## D-011: 書類から発行元が分からないときは、Claude に null を返させて確認待ちに回す

- 日付: 2026-10-28
- 状態: 採用

**背景:** 出力 JSON の `correspondent` は文字列だけを許していた。実機で発行元の書かれていない書類（製品の取扱説明書）を判定させたところ、Claude は「不明」という発行元を返し、ai-classifier はそれを新しい発行元として作った。このままでは「不明」「不詳」「記載なし」のような名前が発行元として増え、無関係な書類が同じフォルダに集まる。

**判断:** `correspondent` に null を許し、プロンプトで「書類から発行元が分からなければ null にし、『不明』のような名前を書かない」と指示する。null は検証で失敗にせず、採用できない発行元と同じく `ai-review` に回す。書類の発行元は空のままなので、ファイルは `未分類/` に置かれる。Paperless の自動マッチで発行元が既に決まっている書類では、null は食い違いとみなさない（これまでの「判定が無ければ見直さない」と同じ）。

**選ばなかった案:** 「不明」などの語を検証で弾く案は、語の一覧が終わらず、弾いたときも結局は確認待ちになる。null を書類起因の失敗として数える案は、発行元の無い書類が 3 回で `ai-failed` に送られてしまう。

## D-012: ページ整形は `edit_pdf` の 1 回の呼び出しで、ページ単位の回転と削除をまとめて行う

- 日付: 2026-10-28
- 状態: 採用

**背景:** 設計書の 6.3 は、ページ単位の編集メソッド（`edit_pdf`）が無いバージョンに備えて、書類全体の回転（`bulk_edit` の `rotate`）とページ削除（`delete_pages`）を別々に呼ぶ縮退運用を用意していた。縮退運用では一部のページだけ向きがずれた書類を自動で直せず、回転と削除で 2 回の再処理を待つことになる。Paperless-ngx 3.3.4 で `edit_pdf` を試したところ、`update_document: true` を付けると、残すページを並べた順に新しい PDF を作り、同じ書類 ID の新しい版として取り込み直すことを確かめた。`operations` に無いページは捨てられ、`rotate` は付けたページだけに効く。

**判断:** ページ整形は `edit_pdf`（`update_document: true`）だけで行い、回転と削除を 1 回の呼び出しにまとめる。ページ単位の回転も自動で直す。縮退運用は使わない。

**選ばなかった案:** 縮退運用を残す案は、3.3.4 では使わない道筋のために判定と呼び出しの組み合わせが倍になり、試験もできない。`update_document: false` で新しい書類を作る案は、書類 ID が変わってタグや分類の続きを引き継げず、元の書類の削除も要る。

## D-013: `edit_pdf` の完了は、書類の版の ID が増えたことで判定する

- 日付: 2026-10-28
- 状態: 採用

**背景:** ページを直した後に分類すると、再処理（OCR のやり直し）が終わる前の古い本文を読んでしまう。`edit_pdf` の応答は `{"result": "OK"}` だけでタスク ID が無く、ai-classifier のユーザーはタスク API（`/api/tasks/`）も読めない。一方、新しい版ができると書類の `versions` に新しい版の ID が増える。

**判断:** `edit_pdf` を呼ぶ前に `versions` の ID を控え、控えに無い ID が現れるまで 5 秒ごとに確かめる。600 秒待っても現れないか、版を読めなければ `page-review` を付けて `ai-todo` へ進める。このとき分類は古い本文を読むことがあるが、人の確認に回るので受け入れる。ページ整形の周期は分類の周期の直前に回すので、待ち終えた書類はその回の分類で処理される。

待っている間に Paperless に繋がらなくなる（`ServiceUnavailable`）、`edit_pdf` の POST がタイムアウトする、待っている間にコンテナが止められる、といった形で周期が途切れると、書類は `page-todo` に残る。`edit_pdf` は既に受け付けられているかもしれない。次の周期で取り込みが終わる前の古い版から operations を計算し直して送ると、Paperless が元にする版をタスクの実行時に決める場合、N ページの版のための operations が既にページを減らした版に当たり、別のページを消しうる。そこで、直す必要があると判定した書類に元の PDF の退避（`/state/originals/{書類ID}.pdf`）が既にあれば、`edit_pdf` を呼ばず、退避も上書きせずに「前回の整形が未確認」として `page-review` を付けて `ai-todo` へ進める。退避があること自体が、前に直そうとした印になる。取り込みが終わっていて直すところが無いと判定した書類は、退避があってもそのまま `ai-todo` へ進める。退避は 90 日残るので、90 日以内に人が `page-todo` を付け直した書類も、直す必要があれば確認待ちになる。これは受け入れる。

ページの整形と版の待ちには最大で書類数 × 600 秒かかり、周期の始めに取った一覧のタグはその間に古くなる。そのため、タグの付け替えでは PATCH の直前に書類のタグを読み直し（`GET /api/documents/{id}/?fields=tags`）、それに `page-todo` を外して `ai-todo`（と `page-review`）を足して送る。待っている間に人が付けた・外したタグを消さないためである。

**選ばなかった案:** タスク API で完了を待つ案は、専用ユーザーにタスクの閲覧権限が要る。本文や `modified` の変化で判定する案は、再処理の途中の状態と区別できない。待たずに次の周期の分類に任せる案は、周期の間隔より再処理が長いと古い本文を読む。

## D-014: ページ整形の失敗は数えず、直さずに `page-review` を付けて分類へ進める

- 日付: 2026-10-28
- 状態: 採用

**背景:** 分類では書類に起因する失敗を 3 回数えて `ai-failed` に送る（設計書 5 章）。ページ整形はその前段で、直せなくても書類の分類はできる。

**判断:** PDF が読めない、`edit_pdf` が 400・403・404 を返す、想定外の例外が出る、といった書類に起因する失敗は回数に数えず、直さずに `page-review` を付けて `ai-todo` へ進める。`ai-failed` は使わない。`edit_pdf` の 403 は書類の所有者が条件に合わないときに書類ごとに起きるので、書類に起因する失敗として扱う。Paperless に繋がらない、401、5xx、元の PDF を退避できない、poppler・tesseract のコマンドが見つからない、といった書類に起因しない失敗（`ServiceUnavailable`）は周期を打ち切り、書類は `page-todo` に残す。タグの読み直しか付け替え（PATCH）が 400・404 を返したときは警告だけを出し、書類は `page-todo` に残って次の周期で判定し直す。ページ整形の周期が打ち切られても、同じ周期の分類は回す。

`page-todo` と `page-review` は必須タグに加える。無ければ分類と同じく起動時に止まる（終了コード 1）。セットアップの手順は初めから 7 つのタグを全部作るので、運用は変わらない。

**選ばなかった案:** 分類と同じく 3 回数えて `ai-failed` に送る案は、ページ整形ができないだけの書類が分類されずに止まる。失敗のたびに周期を打ち切る案は、所有者の合わない 1 件で後ろの書類が整形も分類もされなくなる。

## D-015: ページの判定は poppler・Pillow・tesseract（`osd`）だけで行い、依存を軽くする

- 日付: 2026-10-28
- 状態: 採用

**背景:** 設計書は依存として `pdf2image`・`imagehash`・tesseract の `jpn` を挙げていた。`imagehash` は numpy と scipy を引き込み、イメージが大きくなる。tesseract はページの向きを調べるだけに使う。

**判断:** `pdf2image` は使わず、`pdftoppm` を引数配列で直接呼ぶ。知覚ハッシュは Pillow で dHash（9×8 に縮小し、横に隣り合う画素の大小を並べた 64 ビット）を自前で計算する。tesseract は向き検出（`--psm 0`）だけに使うので、言語データは `osd` だけを入れ、`jpn` は入れない。イメージには `poppler-utils`・`tesseract-ocr`・`tesseract-ocr-osd` を入れる。

**選ばなかった案:** `imagehash` は pHash などの選択肢があるが、連続するページの重複の検出には dHash で足り、数十行の実装のために数十 MB の依存を増やすことになる。`jpn` を入れて ai-classifier 側でも OCR する案は、本文の OCR は Paperless に一本化しており、ページごとのテキストは `pdftotext` で取れるので要らない。

## D-016: ページの判定のしきい値はコードの 1 か所にまとめ、50 ページを超える書類は判定しない

- 日付: 2026-10-28
- 状態: 採用

**背景:** 白紙・重複・向きの判定は、しきい値の決め方しだいで誤削除にも見逃しにもなる。実際のスキャンを見るまで適切な値は分からない。ページ数の多い書類は、ページごとに画像化と向きの検出を行うので判定に時間がかかる。

**判断:** しきい値は `pageplan.Thresholds` の既定値（設計書 6.3 の表）にまとめ、実際のスキャンで調整する。自動で直す範囲と `page-review` に回す範囲の 2 段にし、境界にあるものは人の確認に回す。削除は 1 書類 2 ページまでで、超えるとき・1 ページの書類・全ページが削除候補のときは削除候補をすべて `page-review` にする。白紙の確認待ちになりうるページは向きの検出を省く。50 ページを超える書類は判定せず、`page-review` を付けて `ai-todo` へ進める。

重複ページを自動で削除するのは、空白を除いたテキストが完全に一致するとき（`dup_text_ratio_min` = 1.0）に限る。Paperless-ngx 3.3.4 の試験環境で、同じレイアウト・同じ本文で見出しの 1 語だけが違う 3 ページの合成スキャンを流したところ、別のページが重複として削除された。dHash（64 ビット）の距離は 0、空白を除いたテキストの ratio は約 0.995 で、`dup_hash_max` = 4 と ratio 0.95 の両方を満たした。64 ビットの dHash は同じ書式のページを見分けられず、ratio 0.95 は長い本文の数語の違いを許す。中身のあるページを消すのが最悪の失敗なので、自動削除の条件を締めた。完全に一致しなくても距離が `dup_hash_review_max` 以下なら `page-review` に回す。同じ紙を 2 回読んだ重複でも、OCR の揺れで 1 文字でも違えば確認待ちになる。

**選ばなかった案:** 重複の ratio の下限を 0.95 にする案は、上の実機の結果のとおり同じ書式で 1 語だけ違うページを消す。しきい値を環境変数にする案は、調整の前から設定項目が 11 個増え、値の組み合わせの検証もできない。調整して決まったら変える。50 ページを超える書類も判定する案は、1 書類で周期が長く止まり、後ろの書類の分類が遅れる。

## D-017: ページごとのテキストは OCR 済みのアーカイブ版から、画像は原本から取る

- 日付: 2026-10-28
- 状態: 採用

**背景:** スキャナーは画像だけの PDF を保存し、OCR は Paperless が行う。原本（`/api/documents/{id}/download/?original=true`）にはテキスト層が無く、`pdftotext` は空になる。`original` を付けない `/api/documents/{id}/download/` はアーカイブ版（OCR のテキスト層付き、ページ数は原本と同じ）を返す（Paperless-ngx 3.3.4 で確認）。原本からテキストを取ると、重複ページは `dup_text_min_chars` を満たさず自動では削除されず、白紙の判定はインクだけになる。

**判断:** ページごとのテキストはアーカイブ版から `pdftotext` で取る。画像（インク・dHash・向き）は、`edit_pdf` が書き換え、退避もする原本から取り続ける。アーカイブ版が無い書類では原本が返るので、同じ経路でテキスト層のある原本から取れる。アーカイブ版のページ数が原本と違う、または読めないときは、テキストを全ページ空にして警告を残し、判定を続ける。テキストが空なら重複は自動削除されず確認待ちになるので、安全側に倒れる。ただしテキストが空になると、白紙の判定はインクだけになる。

**選ばなかった案:** 原本から取る案は、実際のスキャンでは常に空になる。アーカイブ版から画像も取る案は、`edit_pdf` が原本を並べ替えるので、判定したページ番号と操作の対象がずれうる。ai-classifier で OCR する案は、OCR を Paperless に一本化する方針（D-015）に反する。
